# Adopt ProjectCompass

Establish project direction and standard documentation homes with operational OutcomeFlow and ChangeShape routing. Audit or advice requests are read-only. Adoption, application, or synchronization authorizes the corresponding documentation migration, not product implementation. Honor the mode and authority already established in the conversation.

## Sources and Discovery

Resolve this skill's symlink to the code-kit root two directories above it, or use the user's source path. Read `docs/workflows/project-compass.md`, `docs/workflows/outcome-flow.md`, and `docs/workflows/change-shape.md`. If a source is unavailable, check known locations before asking; do not invent a substitute. Read the ProjectCompass reference only for document sizing, existing-project migration, or publication-boundary questions, and each reference changelog when upgrading that method.

Inspect the requested project boundary, applicable agent instructions, worktree status, documentation entrypoints, existing direction, active coordination, and delivery rules. Follow links needed to establish ownership or resolve conflicting claims, not every document recursively. Do not inspect private sources, companion repositories, or alternate worktrees outside the authorized scope.

## Audit or Adoption

Map existing information to the contract's standard homes. Check vision and non-goals, roadmap selection and observation, architecture status, selected Shaped specifications, and operating guidance. Existing names do not excuse structural drift; owner-approved exceptions must state the reason and alternative home.

In audit mode, report `compatible`, `partially compatible`, or `adoption recommended`, the document mapping, material gaps, proposed moves, and decisions needed. Report recorded and current versions. Do not edit, format, or create a migration report file.

In adoption mode, establish the standard entrypoints, move or consolidate existing material, and repair inbound references and agent routing. Keep full versioned operating sections in one project-wide workflow document, not in `AGENTS.md`; retain only the contract's compact routing and immediate execution boundaries there. Preserve substantive detail in linked supporting documents rather than reproducing it. Reconcile current selected work and live triggers; create required Shaped specifications without manufacturing candidates or deciding undelegated priorities. New projects may state unresolved architecture choices and no selected outcome honestly.

Apply the adoption and version rules in `skills/adopt-outcome-flow/SKILL.md` and `skills/adopt-change-shape/SKILL.md` from code-kit without requiring separate user invocations. Establish both named contracts; do not substitute a vaguely equivalent method. Avoid duplicate edits when OutcomeFlow adoption already establishes ChangeShape. Do not install other skills or migrate tooling as part of adoption.

Use `docs/workflow.md` by default. Reuse an appropriate existing workflow home; retain `docs/process/workflow.md` when its folder already groups related process documents. Do not create a process subfolder solely for one workflow file or duplicate an existing authority to match the default path.

Ask about consequential conflicts, uncertain loss of material history, or a publication boundary preventing required placement. Continue independent authorized migration; report blocked portions as incomplete. Preserve dirty work and existing review requirements. Structural migration does not authorize branch switching, committing, implementing a feature, or accepting unverified behavior.

## Version and Completion

Keep ProjectCompass's local operating rules in one section, beginning with `Version: x.y.z` from the source. Record OutcomeFlow and ChangeShape separately. If no version is recorded, perform full adoption. For a lower version, apply only entries after it in `docs/workflows/references/project-compass.md`, preserving valid local decisions. Same-version runs still audit and repair drift within authorized scope. A higher recorded version means the source is stale: report it and leave that method's rules and governed structure unchanged. Never downgrade a dependent workflow to complete adoption.

Check the contract's completion conditions against the actual documents and current work, not just headings or version lines. Record a new version only when its required changes are established; report partial adoption and unresolved exceptions accurately. Check moved content for lost obligations, broken links, duplicate authorities, stale status, and accidental permission changes. Confirm agent guidance routes to rather than repeats the workflow sections. Check completed specifications against the contract's promotion, removal, and retention conditions; do not delete unresolved evidence or user history. Run relevant local documentation checks and `git diff --check` where available; repair introduced issues.

Report changes and moves, authoritative homes, versions, material adaptations or approved exceptions, validation, and unresolved decisions. Stop after the authorized planning/adoption work unless the user separately requested implementation.
